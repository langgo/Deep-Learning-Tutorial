二、按场景推荐

场景 1：百万级向量，内存充足，追求极致召回和 QPS（在线推荐/搜索）
首选HNSW —— 召回 99% @ p99 < 5ms，向量数据库事实标准。
备选NSG —— 单层图，内存比 HNSW 省约 30%，但构建更慢。

典型内存开销：128d × 1M × 4B (向量) + M×8B×N (图) ≈ 800MB（M=32）

场景 2：亿级以上向量，内存受限，可接受召回 90%+
首选IVF-PQ —— Faiss 主力方案，内存压缩 16-64x。
进阶IVF-HNSW-PQ —— HNSW 加速粗聚类，PQ 压缩存储，最佳综合。

128d × 1B → 原始 512GB；IVF-PQ (M=16, k=256) → 16GB

场景 3：单机十亿级向量，成本敏感，SSD 部署
首选DiskANN —— 图存 SSD，单机十亿级，微软 Bing 生产验证。
备选SPANN —— 内存头节点 + 磁盘 posting，Bing 生产使用。
场景 4：静态数据集，只读服务，追求上线速度
首选Annoy —— Spotify 出品，构建后 mmap 加载秒级，只读。
备选Faiss IndexFlatL2（小规模）—— 精确 kNN 兜底。
场景 5：文本/文档去重（Jaccard 或 编辑距离近似）
首选MinHash + LSH —— Jaccard 相似度，海量集合去重经典方案。
首选SimHash —— Google 网页去重经典方案，64bit 指纹 + 汉明距离。
场景 6：GPU 加速（超大规模离线检索/训练）
首选Faiss GPU (IVF-Flat / IVF-PQ) —— NVIDIA V100/A100 可达 100 万 QPS。
场景 7：低维（≤20），精确 K-NN 场景（GIS、传感器等）
首选KD-Tree / Ball Tree —— sklearn NearestNeighbors 默认， 低维近似最优。
场景 8：极致 SOTA 召回，Google 内部生态
首选ScaNN —— ICML 2020，ann-benchmarks GloVe/SIFT 领先。
场景 9：高频动态更新（如实时推荐、Feed 索引）
首选HNSW（支持 insert）
避免PQ / OPQ / Annoy（需要重建）

三、决策树：三分钟选出算法

问题 1: 数据规模有多大？ ├─ < 10万 → 暴力搜索 (FlatL2) 或 KD-Tree（低维） ├─ 10万 ~ 1000万 → 进入问题 2 ├─ 1亿 ~ 10亿 → 进入问题 3 └─ > 10亿 → DiskANN / SPANN（SSD） 或 Faiss IVF-PQ 问题 2: 内存是否宽裕？ ├─ 内存充足 → HNSW（推荐）或 NSG ├─ 内存中等 → IVF-Flat 或 Annoy └─ 内存紧张 → IVF-PQ 或 HNSW-PQ 问题 3: 查询延迟目标？ ├─ p99 < 5ms → HNSW / IVF-HNSW-PQ / ScaNN ├─ p99 < 50ms → DiskANN / SPANN └─ 离线批量 → IVF-PQ (Faiss GPU) 问题 4: 是否高频更新？ ├─ 支持在线 insert → HNSW ├─ 每小时重建 → IVF-PQ └─ 静态只读 → Annoy 或 ScaNN 问题 5: 距离度量？ ├─ L2 / 内积 / 余弦 → 上述所有算法 ├─ Jaccard → MinHash + LSH ├─ 汉明距离 → SimHash / BinaryFlat └─ 编辑距离 → LSH-家族的编辑距离 LSH，或专用算法

四、主流开源库映射

Faiss (Meta)

IndexFlat, IVF-Flat, IVF-PQ, IVFADC, HNSW, HNSW-PQ, PQ, OPQ, SQ, ScaNN 兼容。GPU 支持完整。工业界通用首选。

hnswlib

HNSW 官方参考实现（Malkov 团队维护），纯 C++ + Python 绑定。Milvus / Qdrant / Weaviate 底层引用；Elasticsearch 使用 Lucene 自研 Java HNSW（并非依赖 hnswlib）。

Annoy (Spotify)

随机投影树森林，mmap 只读，Python 一等公民。适合静态数据。

ScaNN (Google)

各向异性量化，ann-benchmarks 领跑。TensorFlow 生态。

DiskANN (Microsoft)

Vamana 图存 SSD，单机十亿级低成本。C++ 实现。

NMSLIB

非度量空间通用库，HNSW/NSW/SW-graph 多种图算法。学术研究常用。

向量数据库

Milvus / Qdrant / Weaviate / pgvector / Elasticsearch(Lucene) / Vespa 均以 HNSW 为主力索引；Redis Search 支持 FLAT 与 HNSW 两种，需显式选择。

datasketch (Python)

MinHash / MinHash-LSH / HyperLogLog / SimHash 等草图算法参考库。

五、常见误区与经验

1) "HNSW 一定最快最好"？

HNSW 内存开销大，索引大小是原始向量的 1.5-2 倍。数据规模超过内存限制时，DiskANN/SPANN/IVF-PQ 更合适。 此外 HNSW 构建耗时（O(N log N)），千万级要几十分钟。

2) "PQ 一定损失精度"？

正常配置（M=16, k=256）下 128 维向量的召回损失通常 2-5%。加上 OPQ 或 reordering (精排前 top-100 用原向量重排)， 基本可以恢复到无损。IVF-PQ + reordering 是十亿级场景平衡精度和内存的最佳实践。

3) "召回率数字可信吗"？

Benchmark（如 ann-benchmarks）常用 SIFT1M / GloVe / GIST 等数据集，与真实业务向量分布可能不同。 务必在自己的数据上测试召回-延迟曲线。

4) "调参有什么套路"？

HNSW 建议 M=16-48, efConstruction=200-500, efSearch=50-500； IVF-PQ 建议 nlist ≈ √N, nprobe = nlist/50, M = D/4；召回不够时先加大 efSearch/nprobe， 再考虑改结构。

5) "向量归一化重要吗"？

对于余弦相似度，先做 L2 归一化再用内积或 L2 距离都可以（数学等价）。归一化后所有向量在单位球面上， 量化误差分布更均匀，PQ/OPQ 效果显著提升。
