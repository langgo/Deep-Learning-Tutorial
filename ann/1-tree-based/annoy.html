Annoy · 随机投影树森林

Spotify 开源的近似最近邻算法，用多棵随机超平面树互补覆盖空间。
前置阅读： 向量 / 内积 / L2 范数 基础 KD-Tree Ball Tree 返回总览
关键术语速查（点击展开/收起）
中垂线 / 中垂超平面
到两个点 p 和 q 距离相等的所有点组成的直线（2D）或超平面（高维）。Annoy 每层随机选两点，用它们的中垂超平面作分界。
投影
把一个高维向量映射到某个方向 n 上的标量：proj(x) = ⟨n, x⟩。判断"在超平面哪一侧"，只看这个投影和阈值 b 的大小。
内积 ⟨a, b⟩ (dot product)
⟨a, b⟩ = Σᵢ aᵢbᵢ。可以看作"a 在 b 方向上的投影 × |b|"，也是 cosine 相似度的分子。
随机投影树森林
不追求"最优切法"，而是每层随机选一个方向切一刀；重复建 T 棵这样的树。每棵树独立犯错，但森林一致犯错的概率很小，从而近似覆盖真近邻。
n_trees
森林里树的棵数。越多召回率越高，占内存也越多。Spotify 生产常用 10 ~ 100。
search_k
查询时候选点的下限。越大越准，查询也越慢。经验值 search_k ≈ n_trees × k。
mmap（内存映射文件）
把磁盘文件"直接映射"到进程地址空间，读取就像访问内存。Annoy 索引一旦落盘，多进程可以零拷贝加载，冷启动极快。
candidate set（候选集）
森林查询阶段收集到的所有可能近邻的并集；最后再对候选集精确算距离、排序、返回 top-k。

1. 直观理解

Annoy（Approximate Nearest Neighbors Oh Yeah）由 Spotify 提出， 核心动机：单棵 KD-Tree 或 Ball Tree 在高维下剪枝失效； 与其"更聪明地切一刀"，不如"多切几次、每次都随机"，然后 把多棵树的候选集并起来。

生活化例子：想象你要在一堆散乱的照片中找一张最像目标的照片。

  • 方法 A：让 1 个人按"色调"把照片一分为二 → 大概率漏掉真正相似的照片。
  • 方法 B：让 10 个人各自 随机选一个特征（色调、构图、亮度……）分堆。 把 10 个人各自最相似的一堆照片全部合并 → 目标照片几乎一定在候选集中。

方法 B 就是 Annoy：用多棵结构不同的树来对冲单棵树的偏差。

关键设计

  • 每个内部节点随机选 两个点，取它们的 中垂线（超平面） 作为分界。
  • 每棵树递归到叶节点大小 ≤ K（K ≈ n_trees × 逻辑常数）。
  • 查询：在每棵树上走到叶子并收集候选，用优先队列做 best-first 扩展，直到候选数 ≥ search_k。
  • 最后对所有候选做精确距离排序，返回 top-k。
第一次打开建议这样玩：
  1. 点击 【簇状分布】生成有明显聚集的点，方便观察召回。
  2. 把 n_trees 拉到 1，观察 Annoy 结果（紫色大圈）经常与精确 KNN（绿圈）不一致，召回率会时高时低。
  3. 再把 n_trees 逐步拉到 4、8，观察召回率明显稳定接近 100%——这就是"森林"的力量。
  4. 拖动红色查询点跨越不同区域，注意右侧"每棵树的候选叶"（黄色小点）差异很大——树之间的多样性正是 Annoy 有效的原因。
  5. 最后调节 search_k：调大 → 候选集变大、召回更高、但速度变慢；调小 → 速度快但可能漏掉真近邻。

2. 算法原理

2.1 随机分割超平面

直觉铺垫（几何视角）： 到 p 和 q 距离相等 的所有点，构成的图形就是 p 和 q 的中垂线（2D 是一条直线，高维是一个超平面）。 用一行代数推导：‖x−p‖² = ‖x−q‖²  ⇒  ‖x‖² − 2⟨p, x⟩ + ‖p‖² = ‖x‖² − 2⟨q, x⟩ + ‖q‖²  ⇒  ⟨q−p, x⟩ = (‖q‖² − ‖p‖²) / 2。 令 n = q − p、b = (‖q‖² − ‖p‖²) / 2，这个超平面就是 ⟨n, x⟩ = b。 判断 x 在 p 侧还是 q 侧，只需要看 ⟨n, x⟩ − b 的符号——一次内积搞定。

对当前节点的点集，随机采样两个点 p, q， 分割向量 n = q − p，分割阈值 b = (‖q‖² − ‖p‖²) / 2（欧氏度量下等价于中垂线）。

对任一点 x：side(x) = sign(⟨n, x⟩ − b)；同侧的点归入同一子树。

2.2 构建（伪代码）

def build_tree(points, leaf_size):
    if len(points) <= leaf_size:
        return Leaf(points)
    p, q = random.sample(points, 2)
    n = q - p
    b = (dot(q,q) - dot(p,p)) / 2
    left  = [x for x in points if dot(n, x) <  b]
    right = [x for x in points if dot(n, x) >= b]
    return Split(n, b,
        build_tree(left,  leaf_size),
        build_tree(right, leaf_size),
    )

def build_forest(points, n_trees, leaf_size):
    return [build_tree(points, leaf_size) for _ in range(n_trees)]

2.3 查询（伪代码）

def query(forest, q, k, search_k):
    heap = []                               # (priority, node, tree_id)
    for t_id, tree in enumerate(forest):
        heappush(heap, (INF, tree, t_id))

    candidates = set()
    while heap and len(candidates) < search_k:
        prio, node, tid = heappop(heap)
        if node.is_leaf:
            candidates.update(node.points)
        else:
            margin = dot(node.n, q) - node.b
            # 主侧优先，另一侧按 |margin| 作 penalty 入堆
            near = node.left if margin < 0 else node.right
            far  = node.left if margin >= 0 else node.right
            heappush(heap, (prio, near, tid))
            heappush(heap, (prio + abs(margin), far, tid))

    # 精确排序返回 top-k
    return sorted(candidates, key=lambda x: dist(q,x))[:k]

2.4 为什么森林有效？

每棵树的失误集合彼此独立。假设一棵树把真近邻放到"错的一侧"的概率是 p， 则 t 棵树全部失误的概率约为 pt——指数下降。 这就是 多样性带来的鲁棒性，也是 随机化 与 集成 思路在 ANN 领域的典型应用。

6. 复杂度分析

    

        
            
操作复杂度说明

        
        
            
单棵构建O(N log N)递归深度 log N，每层扫描全体点。

            
森林构建O(T · N log N)T 棵树独立构建，可并行。

            
单次查询O(T log N + search_k · D)先在每棵树上走到叶（对数），再对候选做精确排序。

            
空间O(T · N)每棵树存储 N 个点的分割结构。

        
    

    
召回 vs 速度 trade-off：n_trees ↑ 提高召回、增加构建时间；search_k ↑ 提高召回、增加查询时间。






    
7. 可调参数

    

        
参数控制什么调大的影响调小的影响调节建议

        
            
n_trees召回质量（森林多样性）召回更高，索引内存变大，构建更慢速度快、内存省，召回可能崩塌生产环境 10~100；< 5 通常召回不稳

            
search_k查询速度 vs 精度候选集大，召回高，但查询变慢候选少，查询快，可能漏真近邻经验值 ≈ n_trees × k

            
leaf_size / K叶子容量与内存树浅，叶子内暴力扫描代价上升树深、节点多，内存爆炸默认 K ≈ 2 × n_trees

            
metric距离度量支持 euclidean / manhattan / angular / dot / hamming；切换 metric 需要整体重建索引cosine 用 angular

        
    

    
    
        
  • n_trees：森林大小。Spotify 生产环境常用 10~100。越多越准，占用内存也越大。
    • 
        
  • search_k：查询时候选点数。Annoy 官方推荐 search_k ≈ n_trees × k。
    • 
        
  • leaf_size / K：叶子中最多存的点。默认 K ≈ 2 × n_trees，可用于粗略控制树高。
    • 
        
  • metric：Annoy 支持 euclidean / manhattan / angular / dot / hamming。angular 用于 cosine 相似度。
    • 
    






    
8. 优缺点 & 适用场景

    

        

            
优点

            
    
                
  • 支持 内存映射（mmap），索引可跨进程共享，冷启动极快。
    • 
                
  • 构建后 只读，天然线程安全。
    • 
                
  • 参数少、易调优；召回率高时依然快。
    • 
                
  • C++ 实现，Python 绑定简洁；已在 Spotify 音乐推荐上线多年。
    • 
            

        

        

            
缺点

            
    
                
  • 索引 不可增量更新，新数据必须整体重建。
    • 
                
  • 召回率对 search_k 敏感，可能需要多次调参。
    • 
                
  • 在超高维稀疏数据上不如 HNSW / IVF-PQ。
    • 
            

        

    

    
适用场景：静态推荐候选集（歌曲、商品向量）、嵌入检索、静态知识库向量搜索。






    
9. 代码调用示例

    
Python (annoy)

    
from annoy import AnnoyIndex
import numpy as np

D = 64
index = AnnoyIndex(D, 'angular')         # cosine 相似度
for i, v in enumerate(np.random.rand(10000, D)):
    index.add_item(i, v)

index.build(n_trees=20)                # 一次性构建
index.save('index.ann')

# 查询
q = np.random.rand(D)
ids = index.get_nns_by_vector(q, 10, search_k=200)
print(ids)

10. 常见误区

    

        
初学者容易踩的三个坑

        
    
            
  1. Annoy 是只读结构，插入必须整体重建。 build() 一旦调用就不能再 add_item。想支持增量更新的场景请考虑 HNSW（可以动态添加）或双缓冲重建方案（离线重建 + 在线切换）。
    2. 
            
  2. n_trees 太少召回崩塌，太多内存爆炸。 只建 1~2 棵树时，召回率经常掉到 60% 以下，森林的"多样性对冲"根本没生效；而 1000 棵树也不会显著提升召回，反而占爆内存。生产环境按数据量取 10~100，先跑一次召回评估再调参。
    3. 
            
  3. 不同 metric 需要重建索引。 angular（cosine）和 euclidean 走完全不同的距离运算，索引里保存的分割结构也不同。切换度量必须重新 add_item + build，不能复用旧文件。
