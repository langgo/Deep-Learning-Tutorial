DiskANN / Vamana - 微软的 SSD 图索引

Microsoft Research 2019 提出 - "Fast Accurate Billion-point Nearest Neighbor Search on a Single Node" - 让 SSD 承载十亿级向量索引

前置： NSG（必读，理解 MRNG 单层图） PQ（数据压缩到 SSD 前的量化）
建议顺序： HNSW → NSG → DiskANN (当前) → SPANN
关键术语速查（点击展开/折叠）
Vamana
DiskANN 论文里用的图算法，本质是 NSG 的变种。Vamana 在梵语里是"航行者"。
robust prune
DiskANN 的选边规则。对候选池中的候选按距 p 升序，每选一个 p* 就把"被 p* 覆盖"的候选从池中剔除，直到选够 R 个。
alpha 参数（≥ 1）
Vamana 的松弛因子。alpha=1 时等价于 MRNG（严格剪枝）；alpha>1（如 1.2）保留更多"长跳边"，图更密但搜索跳得远。
PQ 压缩
Product Quantization：把 128 维向量分段量化到 32~64 字节。内存里只存 PQ 码用于粗筛。
SSD IO / 4KB 扇区
一次读 4KB 是磁盘/文件系统的最小读单位，NVMe SSD 一次随机读延迟约 100μs。DiskANN 把每个节点的 完整向量 + 邻居列表 + PQ code 打包到 4KB 一个扇区，一次 IO 拿一整个节点包。
medoid
数据集里距离全体质心最近的实际数据点，用作图的入口。
R-regular 图
每节点度数恰好 R 的规则图。Vamana 构建从随机 R-regular 图开始迭代 refine。
beam width（beam 并发 IO）
beam search 宽度，也是 SSD 并发 IO 数量。beam=4 意味着一次并发发起 4 个 4KB 读。
新手引导（按顺序操作）：
  1. 拖 alpha 滑块到 1.00，点【构建 Vamana】—— 得到严格剪枝的稀疏骨架
  2. 拖 alpha 到 1.20，再次【构建 Vamana】—— 图变密，多了长跳边
  3. 点【对比 alpha=1 vs 1.2】—— 紫色边就是"alpha 增加后新保留的长跳边"
  4. 点【查询模式】后再点画布任意位置，观察 IO 计数（右上角）与 SSD 加载节点
  5. 调 beam width（B）观察 IO 并发对总延迟的影响

一、直观理解：为什么需要 DiskANN？

本方案解决了什么问题： HNSW/NSG 都要求整图在内存里，10 亿 128 维向量 ≈ 500GB 内存，成本天花板极高。DiskANN 把图搬到 SSD，让单台机器承载十亿级索引。
如果不知道 NSG / HNSW 是什么，请先看 HNSW 与 NSG 页面。

HNSW 精度极高，但有个致命瓶颈：整图必须放内存。10 亿 128 维向量约 500GB，单台机器根本装不下。

类比："图存磁盘, 只在内存放导航图"
- 想象一座巨大的图书馆(SSD)存放所有书。
- 内存只放"目录卡片"(压缩向量 PQ)，用于快速筛选。
- 每次查询时，才去 SSD 上拉几十本"真正的书"(完整向量 + 邻居列表)。
- 关键：图必须构建得"每一跳都跳得远"，才能只用几十次 IO 就找到答案。
Vamana = DiskANN 的图算法
"Vamana" 是梵语"航行者"。Vamana 的核心是 alpha 参数控制的 robust prune——比 NSG/HNSW 多一个"松弛因子"，允许保留一些"长跳边"，让搜索能大步前进。
三大关键设计:
1. Vamana 图: 类似 NSG，但用 alpha ≥ 1 松弛剪枝
2. PQ 压缩存内存: 每个向量压缩到 32 字节, 内存中做粗筛
3. 邻居 + 全精度向量共存 SSD: 一次 4KB IO 拿到整个"节点包"

二、算法原理

2.1 Vamana 图构建 (两趟)

  1. 初始化: 随机 R-regular 图 (每节点随机 R 个邻居)
  2. 第一趟: 遍历所有节点, 用 alpha=1.0 剪枝
  3. 第二趟: 再遍历一次, 用 alpha=1.2 (>1) 剪枝, 允许更多长跳边
  4. 入口点: 全体数据的 medoid (类似 NSG 的 navigating point)

2.2 Robust Prune (核心)

Robust Prune (p, V, alpha, R):
V = 候选池 (含所有已访问节点)
while V 非空 且 |neighbors(p)| < R:
 p* = V 中距 p 最近的节点
 把 p* 加入 p 的邻居
 for each v ∈ V:
  if alpha · d(p*, v) ≤ d(p, v): 从 V 移除 v

对比 MRNG (alpha=1.0): "如果 p* 到 v 更近, 则 v 被 p* 覆盖"
Vamana (alpha=1.2): "只有当 p* 到 v 明显更近 (差 20%以上) 才覆盖"

后果: 保留了更多"逃逸边"——从局部聚类跳到远处的边, 让 beam search 早期能大步前进, 减少 SSD IO。

直觉：alpha 越大 → 图越密 → 跳得越远

alpha=1.0：严格剪枝（等价 MRNG / NSG）。只保留三角不等式意义上"不冗余"的边——如果绕 p* 走比直达 v 更近，那 p→v 就被剪掉。图很稀疏。

alpha=1.2：放松。"仅当 1.2·d(p*, v) ≤ d(p, v)（也就是绕 p* 走要比直达短 20% 以上）才剪掉"。保留了更多长跳边，图更密。

为什么更密反而更快？ 长跳边让 beam search 早期能"一步跨很远"，快速到达查询点附近；避免了 alpha=1 时必须走一大串短边才能跨越簇的浪费。
付出的代价：每节点邻居更多（内存/SSD 扇区略大），但换来的 IO 减少（更少跳数）远大于代价。

直觉：SSD IO 与 4KB 扇区

NVMe SSD 一次随机读取延迟约 100μs，一次读 4KB 是硬件 + 文件系统的最小单位——读 100 字节和读 4KB 花的时间几乎相同。

DiskANN 的关键设计：把每个节点的 完整向量（约 512B）+ 邻居列表（R × 4B ≈ 256B）+ 少量元数据 一起塞进一个 4KB 扇区。一次 IO = 拿到一整个节点包，可以立即扩展它的所有邻居。

再乘上 beam=4 的并发：单查询做 50 次 IO ≈ 5000μs = 5ms，与内存 HNSW 的量级已经很接近。

直觉：为什么要两趟构建？

第一趟用 alpha=1.0 建"基础骨架"——严格剪枝，图稀疏但可导航；此时的图相当于一个高质量 MRNG，是良好的初始化。

第二趟用 alpha>1（如 1.2）在骨架上补充"长跳边"——这一趟找到的候选池更靠谱（因为骨架图已经能引导贪心到达合理区域），所以选出的长跳边质量更高。

不能只做一趟 alpha=1.2：起始的随机 R-regular 图太差，贪心找到的候选也差，选出来的长跳边可能只是"运气好"的随机边。

2.3 磁盘布局

SSD 上每个节点占用一个"扇区"(4KB 对齐):
  +--------+---------------------------+--------+
  | vec_id | full_vector (128 * 4B)    | neigh  |
  |  4 B   |         512 B             | R * 4B |
  +--------+---------------------------+--------+
一次 4KB IO 就能读取一个节点的:
  - 完整向量(用于最终精确排序)
  - 邻居列表(用于扩展)

内存: 每个向量的 PQ 压缩 (32-64 字节) + 图入口

2.4 查询流程

function DISK_SEARCH(q, k, L):
    C = beam of size L, init with medoid
    while C has unvisited:
        b = beam of B unvisited nearest in C
        # 并行发起 B 个 SSD IO
        SSD_READ nodes in b        # 得到 full vector + neighbors
        for n in b:
            update PQ_dist for neighbors of n (in memory)
            add neighbors to C, keep top L by PQ_dist
    # 最后, 对 C 中所有节点用 full vector 重排
    return top-k of C by exact dist

六、优缺点 & 适用场景

优点

  • 大规模单机十亿级
  • 省钱成本比 HNSW 分布式方案低 5-10 倍
  • 高召回无损精度设计
  • StreamingFreshDiskANN 支持在线插入删除

缺点

  • 延迟受 SSD 限制, ~5-10ms
  • 硬件依赖 NVMe SSD (不适合 HDD)
  • 构建慢大数据集 3-10 小时
  • 写放大更新时需重写 SSD 扇区

适用场景

  • 数据规模: 亿级 ~ 百亿级
  • 内存受限的成本敏感场景 (RAG 语料库, 图片搜索)
  • 召回要求 > 95% 且延迟可接受 10ms 内
  • 典型用户: Bing 搜索, Azure 认知搜索, Milvus, Weaviate 后端

常见误区

  1. "单机十亿"有前提：需要 NVMe SSD（延迟 100μs 级）+ 可接受 PQ 带来的少量精度损失。SATA SSD/HDD 延迟高一到两个数量级，效果直接打回原形。
  2. beam width 越大不一定越快：并发 IO 打满 SSD 队列深度后延迟不降反升；实际调参一般 beam=4~8。
  3. 构建极慢：几十亿点数十小时是常态。生产上通常离线构建，索引产物直接分发到查询节点。
  4. alpha 太大反而降精度：alpha≥1.5 会保留大量"跨社区"跳跃边，让贪心在早期漂到错误的簇里，返回时来不及精修，反而丢召回。
  5. PQ 精度损失：内存粗筛用的是 PQ 距离，可能漏掉真正的近邻；DiskANN 靠 SSD 加载全精度向量最终重排来补偿，但设置太激进（大 nprobe，小 beam）会让漏检失控。
