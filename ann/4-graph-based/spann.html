SPANN - 内存粗聚类 + 磁盘倒排列表

Microsoft Research NeurIPS 2021 - "SPANN: Highly-efficient Billion-scale ANN Search"
把 IVF 思想推向极致: 内存只放聚类中心, 全部向量放磁盘倒排

前置： IVF-PQ（必读，理解倒排索引） DiskANN（磁盘 IO 基础）
建议顺序： HNSW → NSG → DiskANN → SPANN (当前)
关键术语速查（点击展开/折叠）
posting list（倒排列表）
每个桶（簇）内向量的列表。SPANN 把每个 posting 存到磁盘上一段连续区域，便于顺序读。
head（中心）
每个 posting 对应的桶质心向量，全部驻留内存。查询先用 head 找 nprobe 个候选桶。
边界点复制
处于两个桶交界处的点，同时复制进多个 posting，避免因硬边界漏检。是对经典 IVF 的重要改进。
query-aware truncation（查询感知截断）
查询时按 该 posting head 与查询点的距离比例 截断 posting 尾部——远离查询的 posting 只读少数向量，节省 IO。
gamma（松弛因子）
truncation 的松紧度：gamma 越大保留 posting 越完整（IO 长），gamma 越小截得越激进（快但可能漏）。
SPTAG
微软开源的 ANN 库（Space Partition Tree And Graph），SPANN 用它组织 head 集合上的图导航。
HBC（Hierarchy Balanced Clustering）
层次平衡聚类：递归划分保证 posting 大小均衡，避免 IVF 里常见的"某个桶特别大导致查询慢"问题。
新手引导（按顺序操作）：
  1. 拖 K（簇数）滑块选定 head 数量，点【构建 SPANN】
  2. 观察画布中每个 head（大粉圆）周围的圆环 —— 就是它的 posting list 覆盖范围
  3. 观察橙色白环的点 —— 那是被复制到多个 posting 的边界点（拉大 epsilon 复制率上升）
  4. 拖 nprobe 滑块，点【查询模式】+ 画布任意位置发起查询
  5. 观察 IO 计数 —— nprobe 增大 IO 增多但召回变好

一、直观理解: IVF 的极端形式

本方案解决了什么问题： DiskANN 用随机 IO 访问 SSD，每次拿一个节点；SPANN 换用顺序 IO，一次读一整个 posting（几百个向量）。在同等 SSD 带宽下，顺序读吞吐 5~10× 于随机读，QPS 更高。
如果不熟悉 IVF/PQ 或 DiskANN，请先看 PQ 页面 与 DiskANN 页面。

SPANN 的名字来自 Scalable Partition-based ANN。核心一句话: 把 IVF 的簇心放内存, 所有向量放磁盘, 查询时先在内存找簇再从磁盘拉 posting。

类比: 图书馆的"分类总目 + 分区书架"
- 内存: 只放"分类目录卡"(每类的中心向量, 即 head)
- 磁盘: 每类对应一个"书架格子"(posting list, 存放这类所有真实向量)
- 查询: 先在目录卡里翻找 nprobe 个最相关的类, 再去磁盘对应的格子里精查
对比 DiskANN vs SPANN
- DiskANN: 图结构存磁盘, 一次 IO 读一个节点+邻居, 有依赖(必须走完再读下一个)
- SPANN: 倒排结构存磁盘, 一次读整个 posting list (可能几百个向量), 顺序 IO 更快
核心 4 大关键设计:
1. Hierarchical Balanced Clustering (HBC): 保证每个 posting list 大小均匀 (~100 向量)
2. Duplicating boundary points: 边界点复制到多个 posting, 提升召回
3. Query-aware posting truncation: 查询时提前截断远离查询点的 posting 尾部
4. Head 用图索引组织: 内存的 head 之间用 SPTAG 图导航

二、算法原理

2.1 索引构建

  1. K-Means 递归划分: 用 HBC 把 N 个向量分为 ~ √N 个簇, 每簇约 √N 个向量, 相对均匀
  2. Head 生成: 每簇的中心 c_i 作为该 posting 的 head
  3. 边界点复制: 若点 x 到多个 head 的距离比 (relative distance) < RNG-rule 阈值, 复制 x 到那些 posting (通常一个点复制 8 份)
  4. Head 图: 对 head 集合再建 SPTAG 图 (类似 HNSW), 支持 head 之间快速 nprobe 搜索
  5. 磁盘布局: 每个 posting 存磁盘 (顺序读友好), head 图存内存

2.2 边界点复制规则 (Multi-Assignment)

对于点 x, 找到最近的 head c_1:
 把 x 加入 c_1 的 posting
对次近的 head c_2, c_3, ..., c_k:
 若 d(x, c_i) / d(x, c_1) < epsilon (通常 epsilon ≈ 1.1)
  把 x 也加入 c_i 的 posting
直到复制数达上限 (通常 8)

直观: 处于"两个簇之间"的点会同时出现在两个 posting list, 保证查询任一 posting 都能命中它。

直觉：边界点复制的 RNG 判定

SPANN 的复制规则用相对邻近图（RNG）思想：如果一个点 x 在 head A 与 head B 的"中间地带"，而且 A 和 B 之间没有一个更近的 head 挡在中间，就复制 x 到两个 posting。

反之，如果 A、B 之间还有一个 head C 比 x 更近，那 x 大概率属于 C 的 posting，不需要额外复制到 B。这样能避免"链式复制"导致 SSD 空间爆炸。

本页演示为简化，只用 d(x,c_i)/d(x,c_1) < epsilon 判定，实际 SPANN 会加上 RNG 剪枝。

2.3 查询流程

function SPANN_SEARCH(q, k, nprobe):
    # 阶段 1: 内存搜索 head 图
    top_heads = SPTAG_search(q, nprobe)     # 找 nprobe 个最近 head

    # 阶段 2: 拉取 posting lists 从 SSD (并行 IO)
    candidates = []
    for h in top_heads:
        posting = READ_SSD(h.posting_ptr)    # 顺序读 posting_size 个向量
        # Query-aware truncation:
        # 剪掉 posting 尾部 (dist > threshold) 的向量
        for x in posting:
            if d(q, h) - d(x, h) < gamma * d(q, top_heads[0]):
                candidates.append(x)

    # 阶段 3: 内存中精确排序
    return top-k of candidates by dist(q, ·)

直觉：query-aware truncation 的三角不等式

假设查询 q 的最近 head 是 h_1，距离为 d(q, h_1)。对另一个 head h_i（距离更远），posting 里的一个点 x 到 q 的距离满足：

d(q, x) ≥ |d(q, h_i) − d(x, h_i)|  （三角不等式）

如果右边都已经比 γ · d(q, h_1) 还大，那 x 不可能进入 top-k，可以整段截断。整个 posting list 若都不满足条件，直接跳过整个 posting——省一次 SSD IO。

这就是为什么 SPANN 单次查询实际读的向量数远小于 nprobe × 平均 posting 大小。

2.4 为什么 SPANN 比 IVF 快很多

  • IVF 在内存中做全部工作 (posting 也在内存), 内存开销大
  • SPANN 只把 head 放内存, posting 放磁盘, 内存需求从 O(N) 变 O(√N)
  • Query-aware truncation 让 SSD 顺序读实际只读 posting 的前 30~50%
  • Head 图 (SPTAG) 比 IVF 暴力找 head 快 10 倍

六、优缺点 & 适用场景

优点

  • 内存超省只需 √N 级别
  • 顺序 IOSSD 带宽利用充分
  • 易分片posting 独立可分布式
  • 易增量新数据插入对应 posting 尾部

缺点

  • 召回损失粗聚类 + 硬边界导致漏检
  • 复制开销SSD 空间 2-4 倍原始
  • K-Means 慢大数据集构建耗时
  • 调参多K, nprobe, eps, gamma 需联调

适用场景

  • 数据规模: 10 亿 ~ 万亿级 (SPANN 是当前 SSD 索引的最大规模冠军)
  • 内存资源极度受限, 允许 SSD 换内存
  • 查询 QPS 较低 (< 1000) 且延迟可接受 20-50ms
  • 典型用户: Bing 网页搜索, TikTok 视频推荐, 图片搜索引擎

常见误区

  1. nprobe 大 ≠ 召回线性提升：越靠后的 posting 命中真近邻的概率越低，收益递减。实际 nprobe=8~16 通常已经吃掉召回上限。
  2. 复制上限过大耗尽 SSD：max_replicas=8、epsilon=1.15 时复制率可能达到 3~4× 原始数据；对 10 亿数据集意味着 SSD 从 500GB 涨到 2TB，务必权衡。
  3. head 训练分布不均：K-Means 若初始化差，某些 head 的 posting 会特别大——查询时读它就变成延迟毛刺。这就是 SPANN 必须用 HBC 而不是普通 K-Means 的原因。
  4. gamma 与 nprobe 需联调：只调其中一个可能得不到最优点；生产上通常按召回目标网格搜索 (gamma, nprobe) 对。
  5. 不适合高 QPS 场景：单查询 20~50ms 决定了单机 QPS 上限在几百级别，需要多机复制/分片才能撑起大流量。
